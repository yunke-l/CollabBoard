# Development decisions

## Toolchain

- pnpm workspaces keep the web application, API, and transport contracts in one repository with one lockfile.
- Node.js 24 is the common runtime for local development and CI. TypeScript 5.9 is pinned for legacy NestJS decorator compatibility.
- React and Vite provide the client application. React Router owns navigation and URL filters; TanStack Query owns server data. No duplicate global business store is introduced.
- NestJS runs a modular TypeScript API. Injection tokens are explicit so development and bundled builds do not depend on emitted decorator metadata.
- Plain PostgreSQL SQL migrations keep constraints and transaction boundaries reviewable. The migration runner uses an advisory lock, checksums applied files, and applies each new migration transactionally. Applied migrations are immutable; add a new numbered file for schema changes.
- Vitest checks contracts and database operations. PGlite provides local database tests without Docker; CI repeats the database suite against PostgreSQL 17.
- Local development and CI build the same PostgreSQL image from `infra/postgres/Dockerfile`. It pins official PostgreSQL and Go image digests and verifies the gosu source archive checksum. The gosu 1.20 helper is rebuilt with Go 1.27.4 and `golang.org/x/sys` 0.44.0. The Alpine 3.23 runtime remains on a maintained stable branch and receives available package upgrades during an uncached rebuild. A final filesystem copy excludes replaced binaries from delivered image layers while retaining the package database for vulnerability scans. The official initialization flow, privilege drop, persistent data directory, and fast-shutdown signal are preserved. Unfixed distribution findings remain visible; no scan exclusions are configured.
- Native HTML dialogs provide focus containment and Escape support. Task detail routes reuse the same board context in a desktop side panel and a full-screen mobile dialog.
- CI also starts the compiled API and checks its HTTP boundaries, catching runtime dependency resolution failures that source tests and compilation alone cannot detect.

## Current data integrity

The first migration contains users, projects, project members, tasks, immutable-by-API activity, pending outbox events, and idempotency records. The second migration adds hashed, expiring invitations with one pending invitation per project/email pair. A partial unique index and deferred consistency triggers keep the sole Owner membership aligned with `projects.owner_id`. Active task positions are unique within each project column.

The third migration adds persisted assignment notifications. A composite task/project foreign key prevents inconsistent resource references, and a unique recipient/source-event pair prevents duplicate effects. Task creation and editing insert notifications in their own business transaction after the activity/outbox source event is written. Notification failure rolls back the entire task change. Self-assignment, unchanged assignees, and clearing assignments do not insert rows. The source event ID intentionally has no outbox foreign key, allowing a future outbox retention policy to remove delivered events without erasing notifications.

Project creation locks the owning user to serialize project quota checks. Task creation locks the project before checking membership, quotas, append position, and board revision. Activity, outbox, business data, and idempotency results commit together. Requests replay only for the same authenticated user, operation, request ID, and normalized payload. Task replay rechecks membership and current write capabilities before returning cached results.

Task updates, movement, invitations, and membership changes use the same project lock ordering. Edits and task lifecycle actions compare task versions; moves and project settings actions also compare board revisions. Movement temporarily relocates affected positions, then assigns final contiguous positions in one transaction so the unique active-position index remains enforced throughout. Downgrade, removal, and departure clear active assignments, increment affected task versions, and record changes atomically. Archived tasks retain historical assignees, which are revalidated when restored to the end of their previous column. Real PostgreSQL multi-connection tests verify competing writes, the 500 active task limit, and project quota races.

Project creation, archive/restoration, and ownership transfer acquire user `FOR NO KEY UPDATE` locks before project locks. Transfers lock both involved users in sorted order. These locks serialize ordinary/trial ownership quotas while remaining compatible with foreign-key key-share checks from task and activity writes. Transfer demotes the original Owner before promoting the target, satisfying the immediate partial unique index; deferred consistency triggers verify the final Owner at commit. No schema change is needed for these workflows.

Archived projects freeze content changes, invitation acceptance, and Owner management. A member may still withdraw their own access; the required active-assignment cleanup is an atomic consequence of departure. Owners must restore and transfer ownership before leaving. Mutation replay normally rechecks current membership and capabilities. A completed transfer may be replayed by its original actor while still a member, even though they are now an Editor. A completed departure may be replayed after membership removal, but returns only `{ projectId, left: true }`. Fresh unauthorized requests remain rejected.

Archived-task lists use 20-item cursor pages ordered by millisecond-truncated archive time and task ID. The same tuple is used in the cursor predicate to avoid precision loss across PostgreSQL, JSON, and JavaScript. Parsed cursor timestamps must be canonical ISO UTC timestamps before reaching SQL.

Implemented unbounded lists share a default page size of 20 and accept explicit sizes from 1 to 100. Canonical base64url cursors bind the timestamp/ID boundary to the resource and account or project; authorization remains independent of the cursor and is repeated for every page. The member roster is bounded by the ten-member quota and stays a complete snapshot for assignment and transfer controls. Invitations are a separate Owner-only list of unexpired pending records, with failed-page recovery and refresh after mutation. Its pages remain readable to the current Owner while archived.

Quota conflicts carry a typed `quota` object with the blocking resource, current usage, and limit. These counters come from the quota-enforcing transaction rather than a browser estimate. Total limits take precedence over active limits during creation, because archiving cannot resolve total usage. Restoration checks only active usage. The API error filter preserves validated quota metadata, the OpenAPI schema describes it, and browser forms append usage to the actionable server message without clearing the draft.

Notifications persist identifiers and provenance rather than copied task or project text. Each recipient-scoped list query resolves targets through current membership and project state in one SQL snapshot. An inaccessible or expired target becomes null while the recipient may still read or dismiss the generic notification. Access revocation clears cached notification lists as well as project queries. Unread counters include all received unread rows, including unavailable targets.

The shared database idempotency helper is used by project writes, comment writes, and notification read actions. Bulk reads capture their server time after acquiring the operation lock, preserve PostgreSQL microseconds in SQL, and save the acknowledgement atomically with the read updates. A replay never reruns the bulk update, so later arrivals and late commits remain unread even if their creation timestamps precede the original boundary. Individual reads preserve their first read time. No linked task/project content is stored in these read acknowledgements.

The fourth migration adds independently versioned comments with a composite task/project foreign key. Comment writes use the project lock before reading current membership, including after waiting for another transaction; concurrent edits and deletion cannot resurrect a body or use a role that changed while waiting. Authors edit their own comments; authors and Owners may delete them. Archived tasks allow authorized deletion but reject adding and editing, while archived projects freeze all comment writes. Comment versions do not change task versions, and project revisions reconcile comment counts with board snapshots. Comment, activity, outbox, and idempotency changes commit atomically.

Deleted comments retain a tombstone but physically set their body to null. Comment mutations return identifiers and versions rather than text, so a previously cached create/edit result cannot disclose text after deletion. Immutable history contains only comment identifiers and versions, never comment bodies. Authorized comment reads resolve current author names; activity pages resolve current actor/task names and people referenced by before/after assignment and ownership changes. Comment and activity cursors are scoped to the task or project/filter and use the same millisecond timestamp/ID ordering as other lists.

Invitation credentials are generated by browser Web Crypto using 32 random bytes, passed only in request bodies and URL fragments, and stored only as SHA-256 hashes in the database. Idempotency rows contain input hashes and invitation metadata, never credentials. The browser removes the fragment immediately and temporarily retains the credential in memory/session storage for up to 15 minutes across local sign-in navigation, clearing it on acceptance or cancellation. A retry of invitation creation reuses both the original credential and request ID; generating a replacement revokes the previous pending link.

The browser keeps edit drafts separate from task query snapshots. A conflict refetches saved values but requires an explicit review action before updating the draft's expected version. Offline and Viewer states disable submission while preserving text for copying. An access-denied project refresh clears scoped private queries and returns to Projects. The browser acceptance runner creates and drops a dedicated database and exercises these paths with independent accounts; it does not alter the development database.

## Local adapters and cloud boundaries

The local identity adapter supports email registration, development verification, sign-in, recovery, and synthetic account shortcuts. Salted scrypt password hashes, one-time code hashes, refresh-session hashes, and identity attempt counters live in a private SQLite store outside business PostgreSQL. Codes appear in a development mailbox and no email is sent. One-hour opaque bearer tokens remain in memory; a seven-day absolute HttpOnly, SameSite=Strict refresh cookie restores a session after reload or API restart. Logout and password reset revoke the corresponding stored sessions; bearer authentication checks their revocation. Production and public-interface startup remain rejected.

The fifth migration adds per-recipient deliveries. PostgreSQL locks and expiring tokenized leases coordinate dispatchers; recipients are initialized after business commit and membership is checked again immediately before each publication. Claims and successful acknowledgements are batched to avoid a durable disk flush for every recipient. A process failure before acknowledgement can redeliver an identifier-only hint, which is safe because clients fetch authoritative data. Individual failures preserve successful recipients, use exponential backoff, and become retained failed deliveries after 24 hours. Warnings identify a pending age over 60 seconds or failed deliveries needing manual retry.

The transport boundary has a local in-process SSE implementation. It authorizes only the authenticated user's stream, rejects user-selected/wildcard channels, caps connections, and closes slow or expired sessions. It supports one local API instance; it is not a distributed transport. The browser deduplicates event IDs, reconnects with bounded jitter, and refreshes board/task/member/discussion/file/notification snapshots. Foreground polling and focus reconciliation recover missed hints. Monotonic task and board versions protect against late stale responses; user drafts remain separate from fetched state.

The sixth migration adds private attachment metadata. Quota checks include ready files and unexpired reservations under the project lock. Initialization stores an idempotent metadata result and issues a separately signed, bounded upload capability. The server chooses the key; upload and completion independently check membership and resource state. Completion validates actual size and file characteristics before a transaction marks the file ready, advances board revision, records activity/outbox, and saves its acknowledgement. Rejection is committed before returning its error so that invalid objects cannot retain valid quota. Download capabilities expire within 60 seconds and recheck current access when consumed. Physical removal is retryable; neither the filesystem nor its keys are public routes.

The seventh migration adds a partial unique active-trial index, persistent business rate counters, and an object cleanup queue. User locks serialize trial creation/reset and ownership quotas. Reset expires the original and revokes its invitations while copying synthetic data with fresh IDs in the same transaction. Access checks enforce expiration even if maintenance is delayed. Cleanup queues object keys before cascading trial data deletion. A minute-by-minute worker also handles reservation expiry, rejected/deleted files, orphaned temporary/unknown objects, and configured retention. Rate bucket increments commit together or roll back, allowing multiple API processes to share enforcement even though local SSE itself remains single-instance.

Local private state is selected by absolute `LOCAL_STATE_DIR`, or `.local` relative to the API working directory. Identity/files use private filesystem permissions and stay outside the static web root. Backups must include both PostgreSQL and this state directory with the API stopped for a consistent local snapshot. The automated performance drill restores a frozen logical database into a distinct disposable database and checks exact table digests. It does not claim continuous backup, point-in-time recovery, or cloud RPO/RTO.

AWS integration, Terraform, deployment roles, and paid resources are deferred until local acceptance is complete. The project is intended for a short cloud validation and recording window, followed by resource cleanup.
